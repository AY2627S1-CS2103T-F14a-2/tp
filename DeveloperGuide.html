Design

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

How the architecture components interact with each other

The Sequence Diagram below shows how the components interact with each other for the scenario where the user issues the command delete 1.

Each of the four main components (also shown in the diagram above),

  • defines its API in an interface with the same name as the Component.
  • provides its functionality through a concrete {Component Name}Manager class that implements the corresponding API interface.

For example, the Logic component defines its API in Logic.java and implements it in LogicManager.java. Other components interact with a component through its interface rather than its concrete class, preventing them from coupling to that component's implementation, as illustrated in the following partial class diagram.

The sections below give more details of each component.

UI component

The API of this component is specified in Ui.java

The UI consists of a MainWindow and its parts, such as CommandBox, ResultDisplay, PersonListPanel, UpcomingSessionPanel, ClientDetailPanel, and StatusBarFooter. All of these, including MainWindow, inherit from the abstract UiPart class, which captures common behavior among classes that represent visible GUI parts.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

The UI component,

  • executes user commands using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
  • depends on some classes in the Model component because it displays Person objects from the model.

ResultDisplay measures its wrapped text with a JavaFX Text using the feedback area's font and available width. Its preferred height ranges from 44 to 112 logical pixels, freeing space for the lists after short confirmations. Longer messages remain complete in a wrapping, selectable, read-only TextArea with scrolling. Resizing the window recalculates the height. The surrounding placeholder has no fixed height.

Card typography, selection borders and tag contrast are defined in DarkTheme.css. Both card layouts use the same padding and line spacing. Names, email addresses and record summaries wrap within the card width.

How the Logic component works:

  1. When Logic is called upon to execute a command, the command is passed to an AddressBookParser object, which in turn creates a parser that matches the command (e.g., DeleteCommandParser) and uses it to parse the command.
  2. This results in a Command object (more precisely, an object of one of its subclasses e.g., DeleteCommand) which is executed by the LogicManager.
  3. The command can communicate with the Model when it is executed (e.g. to delete a person).
    Note that although this is shown as a single step in the diagram above for simplicity, the code can require several interactions between the command object and the Model to complete the operation.
  4. The result of the command execution is encapsulated as a CommandResult object which is returned from Logic.

Here are the other classes in Logic (omitted from the class diagram above) that are used for parsing a user command:

How the parsing works:

  • When called upon to parse a user command, the AddressBookParser class creates an XYZCommandParser (XYZ is a placeholder for the specific command name, e.g., AddCommandParser). The parser uses the other classes shown above to parse the user command and create an XYZCommand object (e.g., AddCommand). The AddressBookParser returns that object as a Command object.
  • All XYZCommandParser classes, such as AddCommandParser and DeleteCommandParser, implement the Parser interface so they can be treated similarly where appropriate, for example during testing.

Model component

API : Model.java

Each Person holds contact details, tags, an optional NextSession, an immutable list of Measurement records and a PerformanceHistory. Each measurement has a MeasurementType; the performance history holds GymPerformance records with an ExerciseName and Load. Email is optional, and a client may have no session or progress records. The diagram shows the current model; there is no postal-address field.

The Model component,

  • stores the address book data i.e., all Person objects (which are contained in a UniquePersonList object).
  • stores the Person objects selected by the current filter, such as search results, in a separate filtered list. It exposes this list as an unmodifiable ObservableList<Person> that the UI can observe and bind to, so the UI updates when the list changes.
  • stores the clients with an upcoming session, soonest first, in a separate list built from the whole address book (so find and filter do not affect it). It is exposed as an unmodifiable ObservableList<Person> for the UI's Upcoming sessions panel.
  • stores the client shown by view (or none) and exposes it as an ObservableValue<Person>, so that the UI's detail panel can follow that client.
  • stores a UserPrefs object that represents the user’s preferences (currently, just the GUI settings). This is exposed to the outside as a ReadOnlyUserPrefs object.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

Note: The alternative, arguably more object-oriented, design below keeps a unique list of tags in AddressBook, and each Person references tags from that list. This lets AddressBook maintain one Tag object per unique tag instead of each Person holding its own Tag objects.

Storage component

API : Storage.java

JsonAdaptedPerson stores tags, measurements and gym performances as collections of JsonAdaptedTag, JsonAdaptedMeasurement and JsonAdaptedGymPerformance respectively. The optional next session is stored directly as a String, rather than through a separate adapter. On loading, these values are validated and converted into the corresponding client fields and records; older files without progress collections load with empty histories.

The Storage component,

  • can save both address book data and user preference data in JSON format, and read them back into corresponding objects.
  • is implemented by StorageManager, which delegates the actual JSON file access to JsonAddressBookStorage and JsonUserPrefsStorage (one class per data file).
  • depends on some classes in the Model component (because the Storage component's job is to save/retrieve objects that belong to the Model)

Common classes

Classes used by multiple components are in the seedu.address.commons package.

Implementation

This section describes some noteworthy details on how certain features are implemented.

Application file locations

AppPaths resolves the home folder from its class's CodeSource: a packaged application uses the archive's containing folder, while exploded classes used by IntelliJ or Gradle use the configured working directory. Converting the code-location URL through a URI preserves folder names containing spaces, Unicode and percent signs. An unknown or non-local code location fails explicitly, preventing writes to an unintended fallback folder.

MainApp passes absolute paths for preferences.json and data/spotter.json to the existing storage classes. LogsCenter uses the same home folder during static initialization, before MainApp#init runs. Its FileHandler pattern escapes literal percent signs so folder names cannot be interpreted as logging tokens. If the log file cannot be opened, the already-installed console handler reports the error and remains usable. Client-data save failures retain the existing rollback behaviour.

The path tests package the real resolver and logger into a small executable JAR and launch it in separate JVMs from unrelated folders. This verifies archive detection, special-character paths, existing-data preservation, relaunch behaviour and a blocked log file without changing the test JVM's working directory.

Client name and phone formats

Name and Phone own validation and normalization so command input and JSON loading use the same rules. ParserUtil reports length-specific errors before constructing the value objects. Names are trainer-facing labels, not verified legal identities: the current scope accepts Latin-script letters (including accents), digits 0–9 and the punctuation listed in the User Guide, rather than claiming support for every language.

Name.normalize first normalizes whitespace, then applies Unicode NFC. This gives composed and decomposed versions of the same accented name one stored representation and one length check. Name identity and full-name lookup ignore case and extra whitespace after normalization; search keywords do not yet fold equivalent accent encodings. Accents remain significant: José Tan and Jose Tan are different names. The 100-character limit uses Java string length after normalization, not a count of visually rendered glyphs. No transliteration or compatibility folding is performed.

Phone requires at least three digits and permits English-letter labels and common punctuation within a 50-character normalized value. Plain digits separated by spaces remain stored as digits only for compatibility with older files. Other accepted formatting is retained. This is a contact field, not a dialability validator. getDigits exposes the entire digit sequence; it does not infer country codes, extensions or individual numbers.

Trade-offs: supporting common name formats avoids unnecessary rejection without redesigning command syntax. A space followed by a recognized prefix still starts a new field, and session commands reject slash-containing name identifiers. Those clients remain accessible through displayed indexes. Broader script support and literal prefix escaping require consistent parser, identity, search and storage rules, so they are deferred rather than partially implemented here. These limits do not establish that every user's naming needs are met.

Upcoming sessions panel

The right side of the window shows the clients with an upcoming session, soonest first, so that a trainer can see who is next and prepare. It adds no new session logic. Instead, it reuses what the client list already has:

  • ModelManager keeps a SortedList over a FilteredList of the whole address book. The filter keeps clients whose NextSession is not before "now", which is the same rule that the client card uses to show - (none upcoming). The sort is the existing PersonSessionComparator, so the panel and the client list order sessions in the same way.
  • Each UpcomingSessionCard shows the session time from NextSession#toDisplayString, the phone from PhoneDisplayFormatter, and the latest records from the static PersonCard formatters. The cards have no index numbers, so that they cannot be mistaken for the client list's indices.
  • Booking, cancelling or recording a session replaces the client through Model#setPerson. The FilteredList re-tests the replaced client, so the panel updates without any command knowing about it. Only the passing of time changes nothing in the data, so after each successful command LogicManager#execute calls Model#updateSessionLists(now). Against that one time, it re-sorts the client list (which makes PersonListPanel redraw the client cards) and drops passed sessions from this panel, so both sides agree. It runs only after the command, as re-sorting first could change which client a typed index refers to.

Aspect: when to drop a passed session

  • Alternative 1 (current choice): On the next successful command.
    • Pros: Needs no timer, and the model logic is tested with a fixed "now".
    • Cons: A passed session stays visible until the trainer's next successful command.
  • Alternative 2: On a timer.
    • Pros: Always exact.
    • Cons: Adds a background thread to the UI for little benefit, as the trainer types commands throughout the day.

MainWindow shows either this panel or the ClientDetailPanel in the same place, by binding each panel's visibility to whether Logic#getViewedPerson() holds a client (see View client history).

View client history

view INDEX shows one client's details followed by their full measurement and gym-performance history in the ClientDetailPanel, in place of the Upcoming sessions panel. It follows the usual Logic flow: ViewCommandParser parses the index, and ViewCommand looks the client up in Model#getFilteredPersonList() and passes it to Model#setViewedPerson(Person). The CommandResult only carries a one-line confirmation for the result display.

view is read-only. As LogicManager only saves when a command changes the address book, executing view never writes the data file.

Keeping the panel up to date. ModelManager holds the viewed client in an ObservableValue<Person>, which Logic#getViewedPerson() exposes to the UI. ClientDetailPanel listens to it and redraws whenever it changes. As Person is immutable, a command that changes a client, e.g. edit or measure, replaces it through Model#setPerson(target, editedPerson). If target is the viewed client, ModelManager views editedPerson instead, so the panel follows the client without any command knowing about the panel:

In the same way, Model#deletePerson and Model#setAddressBook (used by clear) stop viewing a client that no longer exists, and ListCommand stops viewing any client. The Upcoming sessions panel then shows again. If saving fails, LogicManager restores the viewed client together with the address book and the filter, so the panel matches the restored data.

Design notes:

  • Non-UI formatter: ClientHistoryFormatter is a plain class in logic.commands with no JavaFX dependency, so the panel's text can be checked in unit tests without starting the GUI. Its detail and record formatting methods supply separate labels in ClientDetailPanel. Measurements and performance have styled headings with counts and a newest-first hint; the formatting and ordering rules are shared with the plain-text formatter.
  • "Now" at drawing time: whether the next session has passed is decided when the panel is drawn, as on the client card. MainWindow also redraws the panel after every successful command, so a session that passes while the panel is open is shown the same way as on the card.
  • Scroll position: when the viewed client changes to a different client (by Person#isSamePerson), the panel scrolls back to the top. A replacement of the same client, e.g. a new record, keeps the scroll position.
  • Ordering: both histories are listed newest first. Measurements on the same date follow the type order weight, body fat, waist. Performance records on the same date are listed most recently recorded first, so the first line always matches the client card's "Latest performance".

Aspect: where to show the history

  • Alternative 1: Show it as text in the result display (used up to v1.4).
    • Pros: Needs no UI changes, and the output is easy to test.
    • Cons: The result display is only a few lines tall, the history is replaced by the next command's result, and it goes stale when the client's records change.
  • Alternative 2 (current choice): Show it on the right side of the window, in place of Upcoming sessions.
    • Pros: Has room for a long history, stays visible while records are logged during a session, and updates as the client changes.
    • Cons: Hides Upcoming sessions until list, and the viewed client must be kept in sync in the model.

Aspect: where to keep the viewed client

  • Alternative 1 (current choice): In ModelManager, updated by setPerson, deletePerson and setAddressBook.
    • Pros: The model is the only place that knows which new Person replaces which old one, and the sync logic can be unit tested without JavaFX.
    • Cons: Adds UI-related state to the model.
  • Alternative 2: In the UI, which would search the client list for the viewed client after every command.
    • Pros: Leaves the model unchanged.
    • Cons: An edited client cannot be matched reliably, e.g. after its name changes, and the logic would be in GUI code that is hard to test.

Recording and deleting gym performances

performance INDEX d/DATE e/EXERCISE s/SETS r/REPS w/LOAD records one result for the client at the displayed index, and deleteperformance INDEX d/DATE e/EXERCISE removes one. Both follow the usual Logic flow: the parser validates the fields, and the command resolves the index against Model#getFilteredPersonList().

The following partial diagram shows how the records are stored and which classes change them. Contact fields and the other progress data are omitted.

Each Person owns one immutable PerformanceHistory, which keeps the records in the order they were recorded and never holds two records for the same exercise on the same date. Exercise names are compared through ExerciseName#equals, which ignores letter case, repeated spaces and the difference between straight (') and curly (’) apostrophes, so a name pasted from formatted text does not split a client's history. PerformanceCommand calls Person#withGymPerformance, which replaces any record for the same exercise and date. DeletePerformanceCommand finds the record through PerformanceHistory#find and calls Person#withoutGymPerformance; a missing record raises a CommandException before any state changes. Either way, the command replaces the client through Model#setPerson, and LogicManager saves the address book.

Both commands log rejected indices, missing records and successful changes at INFO level. The log records the displayed index, exercise and date, but not the client's name or contact details.

Design choice: The client card's latest performance and record count are derived from PerformanceHistory rather than stored separately, so they cannot become stale after a replacement or deletion. Keeping the recording order means the record entered last is treated as the latest when several share a date.

Deleting body measurements

deletemeasure INDEX d/DATE t/TYPE removes one measurement from the client at the displayed index. DeleteMeasureCommandParser validates the index, date and measurement type. The shared ParserUtil#parseCalendarDate accepts future dates because human-edited storage can contain them; parseRecordDate adds the existing future-date restriction for recording measurements and performances. The same calendar parser validates session bookings and date filters, so all date-taking commands share format and impossible-date messages while retaining command-specific usage guidance.

DeleteMeasureCommand looks up the client through Model#getFilteredPersonList() and finds the record by date and type. A missing record raises a CommandException before any state changes. Person#withoutMeasurement creates an immutable copy with that record removed, preserving all contact, session and performance data. Model#setPerson replaces the original client without changing the filter. The card derives its latest measurement and count from the updated list, including same-date type ties and the empty state. History consumers read Person#getMeasurements() from the updated client; a previously formatted history result is a snapshot and must be requested again after deletion.

LogicManager saves the changed address book using the existing storage format. If saving fails, it restores the previous address book and filter and reports Unable to save Spotter data. No storage schema change or separate cached record count is needed. Keeping counts derived from the measurement list avoids stale summary data after deletion.

Session cancellation and date filtering

session distinguishes first bookings, rescheduling and an unchanged booking in its feedback. A replacement includes both old and new timestamps, so the trainer can verify the overwritten slot. Successful bookings restore the full client list and scroll to the top, including after an unchanged booking. Before replacing the booking, the command checks the whole address book for other clients at the same timestamp, excluding the target client. The feedback names these clients alphabetically and keeps both bookings. The check uses exact timestamps: the model has no duration with which to infer an overlapping range.

After a command executes, LogicManager calls Model#updateSessionLists with the current time to refresh the session comparator while preserving the current filter. This also refreshes client card rows through PersonListPanel's existing comparator listener. Refreshing after execution preserves the meaning of displayed indices: a booking that expires while the trainer types must not cause an index-based command to act on a different client. Read-only refreshes never save the data file; rejected commands retain the displayed list.

cancelsession INDEX or cancelsession n/NAME removes a client's single recorded session. CancelSessionCommandParser accepts exactly one index or full name. CancelSessionCommand resolves indices against Model#getFilteredPersonList(), so indices refer to the sorted/filtered UI rather than JSON order. Names use the booking command's case-insensitive, whitespace-normalized matching across the whole address book. This lets a trainer cancel a known client's booking even after indices change or a filter hides the client, while preserving the current filter. Mixed identifiers, empty names and slashes are rejected during parsing. It rejects an invalid index or a client without a recorded session before changing the model. When the cancelled client drops out of the displayed list (e.g. in a sessions date view), the success message adds a note that the clients below have moved up one place, since a repeated index would now refer to a different client.

The following partial model diagram shows the session field, the date predicate and the progress data that must survive cancellation. Contact fields are omitted to keep the diagram focused.

Person#withNextSession(null) returns a new immutable client with the session removed, carrying forward contact details, tags, measurements and performance history. The command replaces the client and reapplies the current predicate to refresh sorting. A session-date predicate no longer matches the cancelled client, so that card disappears from that view; search/tag filters remain active. The observable list updates the UI and CommandResult requests scrolling to the top.

LogicManager handles saving. If storage throws an IOException, its existing transaction restores both the original address book and the predicate captured before cancellation. This restores the booking and the date-filtered view. No constructor, JSON schema or UI-specific cancellation path is needed.

sessions d/DATE uses SessionsCommandParser and ParserUtil#parseCalendarDate to validate one real calendar date. Booking and filtering share this validator, so both accept past dates: a late session can be recorded, and retained expired bookings can be found. SessionCommand notes a past booking in its message instead of rejecting it. SessionsCommand replaces the current predicate with SessionOnDatePredicate and reuses the normal session comparator. It returns a count or a no-matches message. As no client data changes, LogicManager does not save the file.

Design choices: Reusing the current view avoids a second schedule panel or a separate session collection. Retaining the predicate during cancellation lets a trainer cancel several bookings in the same date view. The trade-off is that the date view contains only each client's currently recorded booking; it is not a session history. The main list's upcoming-before-expired ordering also applies to date results, including today's elapsed sessions.

Removing a client's email

edit INDEX e/ with nothing after e/ removes the client's optional email, the same way t/ clears tags. EditCommandParser calls EditPersonDescriptor#removeEmail() for an empty e/ value and parses any other value as before. EditCommand then builds a client without an email, carrying over the other details, the session, measurements and performance history, and replaces the original through Model#setPerson.

Design choice: EditPersonDescriptor stores a plain Email plus an isEmailRemoved flag. setEmail and removeEmail reset each other, so an edit can never both replace and remove the email; EditCommand asserts this. The alternative, an Optional<Email> field that is null when unchanged, made getEmail() return Optional<Optional<Email>>, which reviewers found hard to read.

[Proposed] Undo/redo feature

Proposed Implementation

The proposed undo/redo mechanism is facilitated by VersionedAddressBook. It extends AddressBook with an undo/redo history, stored internally as an addressBookStateList and currentStatePointer. Additionally, it implements the following operations:

  • VersionedAddressBook#commit() -- Saves the current address book state in its history.
  • VersionedAddressBook#undo() -- Restores the previous address book state from its history.
  • VersionedAddressBook#redo() -- Restores a previously undone address book state from its history.

These operations are exposed in the Model interface as Model#commitAddressBook(), Model#undoAddressBook() and Model#redoAddressBook() respectively.

Given below is an example usage scenario and how the undo/redo mechanism behaves at each step.

Step 1. The user launches the application for the first time. The VersionedAddressBook will be initialized with the initial address book state, and the currentStatePointer pointing to that single address book state.

Step 2. The user executes delete 5 command to delete the 5th person in the address book. The delete command calls Model#commitAddressBook(), causing the modified state of the address book after the delete 5 command executes to be saved in the addressBookStateList, and the currentStatePointer is shifted to the newly inserted address book state.

Step 3. The user executes add n/David …​ to add a new person. The add command also calls Model#commitAddressBook(), causing another modified address book state to be saved into the addressBookStateList.

Note: If a command fails its execution, it will not call Model#commitAddressBook(), so the address book state will not be saved into the addressBookStateList.

Step 4. The user now decides that adding the person was a mistake, and decides to undo that action by executing the undo command. The undo command will call Model#undoAddressBook(), which will shift the currentStatePointer once to the left, pointing it to the previous address book state, and restores the address book to that state.

Note: If the currentStatePointer is at index 0, pointing to the initial AddressBook state, then there are no previous AddressBook states to restore. The undo command uses Model#canUndoAddressBook() to check if this is the case. If so, it will return an error to the user rather than attempting to perform the undo.

The redo command does the opposite — it calls Model#redoAddressBook(), which shifts the currentStatePointer once to the right, pointing to the previously undone state, and restores the address book to that state.

Note: If the currentStatePointer is at index addressBookStateList.size() - 1, pointing to the latest address book state, then there are no undone AddressBook states to restore. The redo command uses Model#canRedoAddressBook() to check if this is the case. If so, it will return an error to the user rather than attempting to perform the redo.

Step 5. The user then decides to execute the command list. Commands that do not modify the address book, such as list, will usually not call Model#commitAddressBook(), Model#undoAddressBook() or Model#redoAddressBook(). Thus, the addressBookStateList remains unchanged.

Step 6. The user executes clear, which calls Model#commitAddressBook(). Since the currentStatePointer is not pointing at the end of the addressBookStateList, all address book states after the currentStatePointer will be purged. Reason: It no longer makes sense to redo the add n/David … command. This is the behavior that most modern desktop applications follow.

Appendix: Requirements

Product scope

Target user profile:

  • is a freelance personal trainer who independently manages their own clients, including when attached to a gym
  • manages a client base of tens of clients and handles their own administrative work
  • needs to keep track of client contact details, upcoming session times, body measurements, and gym performance
  • currently keeps client information across contacts, messages, notes, and calendars, making relevant information difficult to retrieve quickly
  • uses a personal computer and is comfortable typing short commands
  • prefers typing to navigating menus for frequent data-entry tasks
  • manages client records individually without requiring shared access with other trainers

Value proposition: Freelance personal trainers manage client information across scattered contacts, notes, and calendars. Spotter brings contact details, session times, and progress records together around each client, helping trainers quickly retrieve information, prepare for sessions, and review progress while spending less time searching across separate tools.

Non-Functional Requirements

  1. Keyboard operation: After launching Spotter, the trainer must be able to complete all core client-management, next-session and progress-recording workflows using the keyboard without requiring mouse interaction.

  2. Capacity and responsiveness: Spotter must support 50 clients, each with up to 1,000 body-measurement entries and 1,000 gym-performance entries. With this dataset, at least 95% of client-listing, client-search and record-update commands must display their results within 1 second on the documented reference computer.

  3. Startup performance: With the dataset specified above, Spotter must load the saved records and become ready to accept commands within 5 seconds on the documented reference computer.

  4. Data integrity: Commands rejected because of invalid input must leave existing client details, next-session information and progress records unchanged.

  5. Storage failure handling: If Spotter cannot save a change, it must display an error indicating that the change has not been saved. If an existing data file is malformed, Spotter must not overwrite that file automatically.

  6. Offline operation: After downloading the release JAR, all core workflows must operate without an internet connection. Spotter must not transmit client records to external services.

  7. Human-editable storage: Spotter must store client records in a documented, plain-text format that can be inspected and edited using a standard text editor while Spotter is closed.

  8. Platform compatibility: Spotter must launch and support all core workflows on mainstream operating systems with Java 25 installed, without requiring another Java version.

  9. Portability: Spotter must be distributed as an executable JAR that runs on a computer with Java 25 installed, without requiring an installer for Spotter.

Glossary

  • Trainer: A freelance personal trainer who independently manages their own clients. The trainer is the user of Spotter.

  • Client: A person whose contact details and training-related information are managed by the trainer in Spotter.

  • Client record: The information stored for a client, including their contact details and any associated session information, progress records, goals, notes and tags.

  • Session: A training appointment between the trainer and a client.

  • Next session: The upcoming training appointment recorded for a client, identified by its date and time. Spotter records at most one next session per client.

  • Body measurement: A numerical measurement of a client's physical characteristics, such as body weight or body-fat percentage.

  • Body-measurement record: A dated entry containing one body measurement for a client, such as body weight, body-fat percentage or waist circumference. A client has at most one record of each measurement type on each date.

  • Gym-performance record: A dated entry describing a client's performance in an exercise, such as the weight lifted or the number of repetitions completed.

  • Progress record / Progress entry: A body-measurement record or gym-performance record associated with a client. These terms refer to the same concept.

  • Progress history: A client's body-measurement and gym-performance records presented together in date order.

  • Goal: A training outcome that a client wants to achieve, such as improving strength or reducing body weight.

  • Session note: A textual description recorded by the trainer after a session to help them prepare for subsequent sessions.

  • Tag: A label attached to a client record to support grouping and filtering, such as rehab or weight-loss.

  • Archived client: A client whose record is retained but excluded from the normal active-client view and can subsequently be restored.

  • Command alias: An alternative name or shortcut for a command.

  • Automatic data persistence: Saving changes without requiring an explicit save command and loading saved data when Spotter starts.

  • Local data file: A file on the trainer's computer containing Spotter's saved records.

  • Human-editable storage: Storage in a documented plain-text format that can be inspected and edited using a standard text editor while Spotter is closed.

  • Sample data: Fictional client records supplied to demonstrate Spotter's behaviour without using real client information.

  • Core workflows: Adding, listing, finding, editing and deleting clients; managing next sessions; recording, viewing, editing and deleting progress entries; managing goals, notes and tags; filtering and sorting clients; archiving and restoring clients; and managing local data, including saving, loading, importing and exporting.

  • Response time: The elapsed time between submitting a command and Spotter displaying its result.

  • Startup time: The elapsed time between starting Spotter and it becoming ready to accept commands after loading saved records.

  • Reference computer: The baseline computer for verifying NFRs 2 and 3: a CPU with four physical cores and a 2.0 GHz base clock, 8 GB RAM, SSD storage, Windows 11 (64-bit) and JDK 25. Performance tests use this configuration with no other user applications running. The exact CPU and SSD models, JDK distribution and version, and operating-system version must be recorded alongside the test results.

  • Offline operation: Operation without an internet connection after downloading the release JAR, on a computer with Java 25 installed.

  • Mainstream OS: For Spotter, Windows, Linux or macOS.

Saving data

Use a copy of the release JAR in a disposable test folder with default configuration and fictional data. The data file below is data/spotter.json inside that folder. Close Spotter before moving, replacing or editing the file. Keep the backup until all tests are complete.

  1. Saving changes across restarts

    1. Launch Spotter and enter add n/Storage Test Client p/91234567.
      Expected: The client appears in the list and the data file is created or updated without a save command.
    2. Enter exit, relaunch Spotter and enter find Storage Test Client.
      Expected: The client is present with phone number 91234567.
    3. Enter exit and copy the data file to data/spotter-backup.json. Use this backup for the recovery test below.

  2. Starting with a missing data file

    1. With Spotter closed, remove data/spotter.json, keeping the backup. Relaunch Spotter.
      Expected: Spotter shows its sample clients rather than the previously saved test client.
    2. Enter exit.

  3. Starting with a corrupted data file

    1. With Spotter closed, create data/spotter.json containing only not valid JSON. Relaunch Spotter.
      Expected: No clients are shown. Spotter displays Unable to load saved Spotter data. The existing data file has not been modified.
    2. Enter list, then exit. Open the data file in a text editor.
      Expected: The file still contains exactly not valid JSON; startup, listing and shutdown have not overwritten it.
    3. Relaunch Spotter and enter add n/Recovery Test Client p/92345678, then exit.
      Expected: The successful data-changing command replaces the corrupted file with valid JSON.
    4. Relaunch Spotter.
      Expected: The recovery test client is present with phone number 92345678, and no load warning appears. Enter exit.

  4. Starting with a data file containing invalid values

    1. With Spotter closed, replace data/spotter.json with a copy of data/spotter-backup.json. Open it in a text editor and change the phone number 91234567 to 12, keeping the JSON valid. Relaunch Spotter.
      Expected: No clients are shown, not even those with valid values. Spotter displays the same load warning as for a corrupted file.
    2. Enter list, then exit.
      Expected: The data file still contains phone number 12. Other invalid values, such as an email without @, a measurement outside its range, or two measurements of the same type on the same date, behave the same. Exception: a measurement or performance dated in the future is not invalid. Spotter loads it normally, because future dates are only rejected when a record is entered with a command.

  5. Restoring a valid backup

    1. With Spotter closed, replace data/spotter.json with a copy of data/spotter-backup.json. Relaunch Spotter and enter list.
      Expected: The original saved clients, including Storage Test Client with phone number 91234567, are restored. Recovery Test Client is absent, and no load warning appears.

Preserve a backup before testing corrupted data. The damaged file is retained only until a successful command changes client data; that command overwrites it with the current records.
